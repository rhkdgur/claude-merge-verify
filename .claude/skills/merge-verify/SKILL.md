# 머지 검증 (merge-verify)

브랜치 머지 중 발생한 충돌을 해결한 결과가 올바른지 3-way diff로 검증한다.
**충돌 없이 자동 병합된 파일은 검증 대상이 아니다 — 실제로 충돌이 나서 사람이 손으로 해결한 파일만 본다.**

**전제조건 1: 커밋 이전 상태에서만 쓴다.** 이 skill은 머지 커밋이 만들어지기 전(`MERGE_HEAD`가
아직 존재하는 상태)에만 적용된다. 이미 머지 커밋을 만든 뒤라면 이 skill의 적용 대상이 아니므로,
그 사실을 사용자에게 안내하고 종료한다(다음부터는 커밋 전에 검증하도록 안내). 원격과의
divergence·push 가능 여부 체크는 이 skill의 범위가 아니다(별도 요청 시 그때그때 처리).

**전제조건 2: 이 skill은 사용자가 이미 직접 병합·충돌 해결을 진행 중인 상태를 검증하는 용도다.**
병합을 새로 시작하는 것은 이 skill의 역할이 아니다 — 오직 "이미 벌어지고 있는 병합 결과"를
읽기 전용으로 검증하고 보고한다.

읽기 위주 조사(status/diff/log/grep)만 자유롭게 수행하고, working tree/index를 바꾸는 조작
(충돌 파일 수정, 커밋)은 **어떤 것도 대신 실행하지 않는다.** 문제를 발견하면 "무엇이 문제인지 +
어떻게 고쳐야 하는지"까지만 보고하고, 실행은 전적으로 사용자에게 맡긴다. 다만 사용자가 별도로
명시적인 수정 지시("이 버그 고쳐줘" 등)를 하면 그건 이 skill 범위 밖의 요청으로 취급해 통상적인
방식대로(사용자 확인 후) 수행한다.

## 0. 적용 가능 상태인지 확인

```bash
git status
git rev-parse -q --verify MERGE_HEAD   # 값이 없으면(실패하면) 이미 커밋됨 → 이 skill 적용 대상 아님
```
`MERGE_HEAD`가 없으면 즉시 중단하고 사용자에게 "이미 커밋된 상태라 이 skill은 적용할 수 없다,
다음엔 커밋 전에 요청해달라"고 안내한다.

## 1. 3-way 기준점 확보

```bash
git rev-parse HEAD         # ours (머지 진행 중엔 아직 커밋 안 해서 HEAD가 그대로 머지 전 로컬 브랜치)
git rev-parse MERGE_HEAD   # theirs (병합해오는 브랜치)
git merge-base HEAD MERGE_HEAD   # base (공통 조상)
```
`ORIG_HEAD`는 쓰지 않는다 — 보통 `HEAD`와 같은 값이지만, 병합 도중 다른 `reset`/`checkout` 등이
끼어들면 값이 바뀔 수 있어 덜 안전하다. `HEAD`는 머지가 아직 커밋되지 않은 한 절대 움직이지 않으므로
그 자체가 곧 "머지 전 상태"다.

## 2. 실제 충돌났던 파일만 정확히 뽑기 (토큰 절약 핵심)

`git merge-tree`로 워킹트리·인덱스를 전혀 건드리지 않고 3-way 병합을 다시 계산해서,
실제로 충돌이 났던 파일만 정확히 골라낸다. 사용자가 이미 충돌을 해결해서 `git add`까지
끝내놨어도(더 이상 `git status`로는 "어떤 파일이 충돌이었는지" 알 수 없는 상태여도) 이 방법은
영향받지 않는다 — base/ours/theirs 커밋 자체를 가지고 순수하게 재계산하기 때문이다.

```bash
git merge-tree --write-tree HEAD MERGE_HEAD
```
출력 앞부분엔 충돌난 경로마다 `<모드> <sha> <stage>\t<경로>` 형식의 줄이 stage 1(base)/2(ours)/3(theirs)
세 개씩 나온다(그 뒤에 이어지는 `CONFLICT (...)` 텍스트 메시지는 충돌 종류마다 문구가 달라 파싱에
안 쓴다). 이 stage 줄에서 경로만 뽑아 유일화한다:
```bash
git merge-tree --write-tree HEAD MERGE_HEAD | awk '$3 ~ /^[123]$/ {print $4}' | sort -u
```
이 목록에 없는 파일은 git이 자동으로 합친 것이 확실하므로 **검증 대상에서 완전히 제외한다**
(3번을 수행하지 않는다).

추가로, 이미 충돌 해결 후 손을 더 댄 흔적이 있는 파일도 포함시킨다:
```bash
git status --short | grep '^MM'   # staged 해결본 + unstaged 추가수정이 공존하는 파일
```
`MM` 파일은 `merge-tree` 목록에 없어도 항상 3번 검증 대상에 포함한다(추가 수정 자체가 새로운 실수의 원인이 될 수 있음).

## 3. 대상 파일에 대한 3-way 정밀 검증 (핵심)

2번에서 추려진 "실제 충돌났던 파일 + MM 파일"에 대해서만 수행한다. 이 대상 파일 수가 많으면
(대략 5개 이상) **general-purpose 서브에이전트에 위임**해서 메인 컨텍스트를 아끼고, 아래 지시를
그대로 프롬프트에 포함시킨다:

```bash
git diff <base> <ours>   -- <file>   # ours가 뭘 바꿨는지 (전체 내용)
git diff <base> <theirs> -- <file>   # theirs가 뭘 바꿨는지 (전체 내용)

# 실제 해결 결과(파일 전체 내용)를 볼 때는 콜론(:) 문법을 쓰고 `--`는 붙이지 않는다
git show :<file>   # 인덱스(stage 0, 충돌 해결 후 staged된 내용)
# 아직 add 전이라면 워킹트리 파일을 직접 Read
# 위 문법에 `-- <file>`을 덧붙이면 안 된다(그러면 파일 내용이 아니라 diff가 나옴)
```
찾아야 할 것:
1. **코드 누락**: 한쪽에서만 추가/수정한 로직이 해결 결과에 빠짐
2. **중복 반영**: 같은 로직(메서드/import/필드/설정)이 두 번 들어감
3. **논리적 충돌**: 양쪽 변경을 기계적으로 합쳤지만 의미가 안 맞음
   (예: 한쪽이 만든 변수를 다른 쪽이 쓰기로 리팩터링했는데, 해결 결과에서 그 변수 사용이 빠지고
   옛 변수를 그대로 참조 — 컴파일은 되지만 기능이 깨지는 회귀. 반드시 코드를 읽고 의미까지 확인해야 함)

## 4. 충돌 마커 잔존 여부 재검사 (대상 파일 한정)

```bash
# 워킹트리 기준. 2번에서 추린 대상 파일들만 지정해서 검사한다

```

## 5. 컴파일 검증에 대한 한계

이 skill은 코드를 읽고 import/타입/시그니처를 대조하는 방식으로 "컴파일될 것 같다"를 판단하는 것이지,
실제 빌드를 돌려서 검증하는 단계는 포함하지 않는다. `mvn`(또는 빌드 도구)이 설치돼 있다면
`mvn compile` 같은 실제 컴파일을 별도로 한 번 돌려보길 권고하되, 이 skill의 필수 절차로 강제하지는 않는다.

## 6. 최종 보고 형식

- 2번에서 검증 대상으로 잡은 파일 목록과, 제외한(자동 병합된) 파일 수를 먼저 밝힌다
- 대상 파일별: 이상 없음 / 의심 항목(파일:라인, 누락·중복 내용, 근거 diff)
- 회귀 버그가 실제 코드 흐름을 깨는 경우는 우선순위 높음으로 표시하고 수정 여부를 사용자에게 확인
- **커밋은 절대 대신 실행하지 않고**, 검증 결과 문제가 없으면 "커밋하셔도 됩니다" 정도로만 안내하고 끝낸다
